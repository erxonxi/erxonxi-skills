# Domain modeling

TypeScript-like notation for illustration only. If the project already has aggregates, copy their exact shape.

## Where each rule lives

Order of preference, from most protected to least:

1. **Value object constructor**: a rule about a single value (format, range, length).
2. **Aggregate** (constructor or behavior method): a rule that combines several fields of the aggregate.
3. **Domain service** (stateless, in `domain`): a rule that needs several aggregates or a repository (`UserFinder`, `...CriteriaFactory`).
4. **Use case**: orchestration and checks that depend on repositories (existence, uniqueness).

A rule lives in exactly one place. If a rule can be bypassed by building the object directly, it is in the wrong place. The database constraint is a safety net, not the place of the rule: the domain does not depend on engine error codes.

## Aggregate

```ts
class User extends AggregateRoot {
  private constructor(readonly id: UserId, private name: UserName, private email: UserEmail) { super(); }

  static create(id: string, name: string, email: string): User {
    const user = new User(new UserId(id), new UserName(name), new UserEmail(email));
    user.record(new UserRegisteredDomainEvent(id, name, email));
    return user;
  }

  static fromPrimitives(p: UserPrimitives): User { /* rebuilds, records no events */ }
  toPrimitives(): UserPrimitives { /* the only way to serialize */ }

  updateEmail(email: string): void {
    this.email = new UserEmail(email);
    this.record(new UserEmailUpdatedDomainEvent(this.id.value, email));
  }
}
```

- Private constructor. Create with a named constructor (`create`, or a business verb) that records the creation event. Rebuild from persistence with `fromPrimitives`, which never records events.
- `toPrimitives()` is the only form of serialization. Domain objects do not leave the module: primitives or DTOs do.
- State is private and immutable by default. No setters. Changes are methods named after business intent (`rename`, `archive`, `publish`, `addCategory`), which revalidate and record their event.
- The `AggregateRoot` base stores the events: a protected `record(event)` and `pullDomainEvents()`, which returns and clears them.
- Small aggregates. Reference other aggregates by id (a value object), never by object. Split into two aggregates when one part changes without the other or when loading the whole to modify the part is expensive.
- If an aggregate needs read-only data from another, copy the necessary primitives and keep them up to date with an event subscriber.
- Variants with different data or behavior: subclasses or a strategy, not a `type` field with conditionals.
- Ids come from outside (generated by the client) and are validated as a value object. Sequential business numbers are assigned by a repository method (`nextNumber`).
- A projection or read model may be a plain data object. The rich model is for the write side.

## Value objects

- Wrap every primitive that has identity, a rule or a unit: ids, email, name, amount, date range, score.
- Validate in the constructor and throw a named domain error. An invalid value cannot be constructed.
- Immutable. Equality by value (class and value), never by reference. Be careful when looking up value objects in collections with identity operators.
- Generic bases in the shared kernel (`ValueObject<T>`, `StringValueObject`, `Uuid`/`Identifier`, `Enum`). Concrete subclasses are empty when they only add type and name (`UserId extends Uuid`).
- Composite value objects validate across fields (`DateRange` requires start before end). Collections with their own rule are their own type, in plural (`Reservations` prevents overlapping dates).
- Do not wrap by reflex: if the value has no rule, identity or unit and only lives in a read model, a primitive is enough.
- If the language allows it, derive the primitives type from the aggregate itself instead of maintaining parallel DTOs by hand.

## Domain events

- Class name: subject + past-tense verb + `DomainEvent` (`UserRegisteredDomainEvent`, `ProductRenamedDomainEvent`).
- Message name: `<company>.<context>.<aggregate>.<fact>` in lowercase with dots and `snake_case` for compound words: `acme.shop.user.registered`, `acme.catalog.product.category_added`.
- Name the business fact, not the field change: `UserArchived`, not `UserStatusUpdated`. One event per meaningful change: `UserEmailUpdated`, not a `UserUpdated` carrying the whole state.
- Immutable. Primitives only. Always carries `aggregateId`, `eventId` and `occurredOn`, plus the data that changed or that the subscriber needs so it does not have to ask again.
- Recorded inside the aggregate. Published by the use case after saving: `eventBus.publish(aggregate.pullDomainEvents())`. The domain never publishes or does input/output.
- Subscriber: one class per reaction, named `<Action>On<Event>` (`SendWelcomeEmailOnUserRegistered`), which declares which events it subscribes to and delegates to a use case. Its stable name `<company>.<context>.<action>_on_<event>` identifies its queue (`acme.notifications.send_welcome_email_on_user_registered`).
- Delivery is "at least once" with no guaranteed order: subscribers must be idempotent and tolerate duplicates and reordering.

## Domain errors

- One class per condition, with a business name, extending a common base (`DomainError`). It carries structured data (the id, the rejected value), not just text.
- Names: `UserDoesNotExistError`, `ProductNameTooLongError`, `ReviewAlreadyExistsError`. Pick one suffix and keep it across the project.
- Never generic errors, error codes (`-1`), `null`/`false` as a failure signal, or decisions based on the message text.
- They are thrown in the domain (value object constructor, aggregate method, finder). In languages whose idiom is error values, return sentinel or typed errors with the same naming criteria.
- Infrastructure errors (connection, timeout) are not domain errors and are not disguised as them.
- They are translated to the protocol only at the entry point, with an explicit and exhaustive error → status mapping. Anything unrecognized is a 500 that does not leak the message. Mapping reference: 400 malformed input, 404 does not exist, 409 state conflict or duplicate, 422 business invariant violated.
- The error name is part of the public contract (`{ error: { type, message } }`): renaming it is a breaking change.

## Repositories

- One port per aggregate root, declared in `domain` (`UserRepository`). Implementations in `infrastructure` with the technology as prefix (`PostgresUserRepository`, `InMemoryUserRepository`).
- They receive and return whole aggregates, never rows or DTOs.
- Minimal API. Vocabulary:
  - `save(aggregate)`: create or update.
  - `search(id)`: returns the aggregate or nothing (nullable/optional).
  - `searchAll()`, `searchByIds(ids)`.
  - `matching(criteria)`: queries with filters.
- **`search` may find nothing. `find` throws if it does not exist.** `find` is not in the repository: it lives in a finder (`UserFinder`) that calls `search` and throws `UserDoesNotExistError`. `get` is avoided as ambiguous.
- Do not add a method for each combination of filters. For flexible queries use Criteria.

### Criteria

- `Criteria` = `Filters` (a list of `Filter { field, operator, value }`) + `Order { orderBy, orderType }` + optional pagination.
- It lives in the shared kernel. Infrastructure translates it to each target with a converter per technology (SQL, Elasticsearch, ORM), always with bound parameters, never interpolating values.
- Named business queries are factories in `domain` (`InactiveCustomersCriteriaFactory.create()`).

## Read models and projections

Step up one rung only when the previous one hurts:

1. Compose in the query (join in the repository).
2. SQL view.
3. Materialized view.
4. Projection maintained by event subscribers (derived data stored in the aggregate itself or in a read store).

- Projection subscribers are named the same way: `IncrementCustomerTotalOrdersOnOrderPlaced`.
- A projection may reuse the same repository port with another adapter.
- Eventual consistency between write and read is accepted.

## Naming

| Thing | Convention | Example |
|---|---|---|
| Language | English, business terms (ubiquitous language) | `ban`, not `block`, if the business says "ban" |
| Id | `<Aggregate>Id` | `ProductId` |
| Typed collection | Plural | `OrderLines`, `Reservations` |
| Boolean | `is*`, `has*`, positive | `isBanned`, `hasCategory` |
| Guard | `ensure*` (throws) | `ensureEmailIsValid` |
| Named constructor | `create`, `fromPrimitives`, business verb | `Order.create(...)` |
| Event | Past tense + `DomainEvent` | `UserRegisteredDomainEvent` |
| Subscriber | `<Action>On<Event>` | `SendWelcomeEmailOnUserRegistered` |
| Error | Condition + suffix | `UserDoesNotExistError` |
| Non-persistent output port | Role + `Gateway`/role | `EmailSender`, `ProductRecommendationsGenerator` |

## What to avoid

- Anemic model with getters and setters on the write side.
- ORM or framework annotations in domain classes.
- Primitive obsession in aggregates and domain signatures.
- Publishing events or doing input/output from the domain.
- Generic "updated" events carrying the whole state.
- Exposing aggregates outside their context.
- Default parameters that hide how an object is built.

## Template for designing an aggregate before coding it

```
Name · Description · Context
Properties (with type if known)
Invariants it enforces
Corrective policies (what happens when an invariant is violated)
Domain events it emits
Access patterns (search by id, by ...)
```

From this you derive: the module in plural, the aggregate, one event per mutation, one error per invariant, the repository port, one use case per mutation and per query, one test per use case, one Object Mother per aggregate and value object, and the repository implementation with its test.
